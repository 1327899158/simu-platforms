# 工程师案例展示与等级晋升

## 本次功能

工程师进入“我的 → 案例展示”，从本人已完成且未删除的承接订单中选择项目，另行填写公开标题与介绍，确认不含客户机密且已取得必要展示授权后保存。可编辑、移除、预览，每位工程师最多 40 个案例；订单候选列表每页 20 笔。移除仅删除案例，不删除订单、报价或成果文件。

客户点击首页推荐工程师、工程师目录卡片或订单报价中的资料入口，可在同一资料页看到头像、昵称、简介、专业方向、软件、等级标签、精选案例和客户评价；保留独立的“发起沟通”操作。公开案例每页 6 条，可继续加载。

案例采用字段白名单：只返回案例 ID、公开标题、介绍、方向、软件和完成月份。不会返回原订单 ID、订单号、金额、客户信息、订单原文或成果文件，也不会把“公开介绍”自动填成原始需求。第一版为文字案例卡片，不复制云附件或生成虚构图片。

公开查询每次校验原订单仍为 COMPLETED、选中工程师匹配、工程师账号有效且认证通过。订单进入纠纷/重新执行等状态或认证失效后，下次加载时停止公开；管理页保留条目并提示暂停展示，恢复条件后再次显示。已被客户看到或另行保存的内容无法追回，发布前仍须确认保密与授权。

## 等级规则与自动更新

沿用既有规则，没有提高样本门槛或修改支付费率：

| 头衔 | 累计完成单量起点 | 好评率 | 纠纷率 |
| --- | --- | --- | --- |
| 认证工程师 | 0 | 不要求 | 不要求 |
| 新秀工程师 | 1 | ≥85% | 不要求 |
| 成长工程师 | 10 | ≥90% | 不要求 |
| 资深工程师 | 30 | ≥95% | <2% |
| 金牌交付工程师 | 60 | ≥97% | <1% |
| 首席工程师 | 120 | ≥98% | <0.5% |

所有等级的前提是实名认证通过并提交基础资质文件（identity_verification_files 中的 SUPPORTING 记录）。仅把认证状态手动改成 APPROVED、但没有任何资质材料的测试账号，仍会显示“待完善资质”，不能凭空晋级。

- 完成单量：沿用 completedAt 非空的累计订单数，而非仅计算目前为 COMPLETED 的订单。
- 好评率：客户给工程师的综合评分 ≥4 的评价占比；无评价不视为 100%。工程师给客户的私有评价不计入本人等级。
- 纠纷率：已付款承接订单中发生过纠纷的去重订单数占比，包含已取消的历史纠纷；严格小于的门槛不包含等于。
- 按当前实际符合条件的最高头衔评定；高单量但评分未达标时显示较低头衔，指标下降也会重新评定。不永久锁定历史最高头衔。
- 正常验收、客户新增/修改评价、管理员身份审核、发起/取消/仲裁纠纷后刷新等级缓存；“我的”、等级页、公开资料、工程师列表及报价列表查询时重新计算兜底，不需要手动点击升级。
- 晋级页显示下一头衔、单量差距、好评率/纠纷率是否满足。单量进度条不是全部晋级条件的综合百分比。
- “我的”按账号缓存上次展示头衔，检测提升后给出提示；不新增短信、推送消息或后台定时任务。
- 15%、10%、8% 仍为预留规则，未接入扣款或分账。

## 数据库与部署

1. 先部署当前后端，再编译/发布小程序。后端启动的 db.init() 会自动创建 engineer_cases，home-migration 会检查既有等级统计字段。
2. 独立迁移命令 npm run migrate 现在也会执行 home-migration，避免只建业务表却缺少等级字段。迁移命令会写数据库，只在目标环境由维护者执行；本次开发未执行到云数据库。
3. 如部署后仍提示 engineer_cases 不存在，可在正确数据库执行同目录 engineer-cases-table.sql 中单独的一条 CREATE TABLE。只复制 SQL 正文，不包含 Markdown 标记，不要整段提交多条 SQL。
4. 当前工程师等级继续持久化到 engineer_profiles 的 levelKey、completedOrderCount、positiveReviewRate、disputeRate、levelUpdatedAt 字段，没有另建一套手工头衔。
5. Prisma 蓝图同步增加 EngineerCase 及关系。实际 Node 服务仍使用 db.js/mysql2，不应直接用 Prisma migrate 替代本项目的迁移。

## 接口

| 方法 | 路径（均以 /api 开头） | 说明 |
| --- | --- | --- |
| GET | /engineers/me/cases | 工程师本人案例管理列表（包含暂停项） |
| GET | /engineers/me/case-candidates?offset=0 | 本人已完成订单，包含是否已添加标识 |
| POST | /engineers/me/cases | 新增：orderId、title、summary、confirmPublic=true |
| PATCH | /engineers/me/cases/:id | 编辑：同上，不能改绑其他订单或工程师 |
| DELETE | /engineers/me/cases/:id | 移除本人案例，认证失效仍允许撤下 |
| GET | /engineers/:id/cases?offset=0 | 已登录用户查看公开案例 |
| GET | /engineers/:id/profile | 新增 level、cases（首批案例） |
| GET | /engineers/level | current 新增 advancement（下一等级与差距） |

## 测试与验收

本地 Node 测试共 51 项顶层测试通过；新增覆盖案例归属、订单状态、认证、公开授权确认、唯一性/数量上限、字段白名单、移除范围、晋级落库与边界、页面选择/编辑/公开资料加载和建表一致性。测试数据库和小程序 Page 是模拟对象，不能替代 TDSQL 真实并发、微信编译及真机验收。

建议用独立测试环境验证：

1. 工程师 E 拥有一笔已完成订单 O 和一笔执行中订单；案例选择只出现 O。另一工程师不能提交 O 的案例。
2. 给 O 添加不含客户私密信息的标题/介绍，客户从首页点击 E，确认案例与等级标签可见；客户网络响应不含 O 的订单 ID/金额/文件 ID。
3. 编辑介绍后刷新客户资料确认变化；移除后案例消失，原订单及文件仍存在。
4. 将 O 按正常流程发起纠纷，客户刷新后案例隐藏，工程师管理页显示暂停。取消纠纷恢复 COMPLETED 后再次展示。
5. 新工程师通过认证并实际上传基础资质材料，完成 1 单且获得达标评价，应成为新秀。准备 9→10、29→30、59→60、119→120 单的测试数据，配合达到/低于好评率及纠纷率边界，核对头衔与下一等级差距。
6. 纠纷率正好等于 2%、1%、0.5% 时不得升级至对应等级；无客户评价不能晋升新秀以上；只给客户写评价不增加本人的好评数。
7. 在“我的”、首页推荐、工程师目录、报价卡和公开资料页对比同一工程师标签，应采用同一等级服务结果。若测试 SQL 账号没有资质附件，先通过实际资料流程补齐并审核，不要伪造 cloud fileID。

本次未部署、未修改线上账号/订单/资质，也未向客户发送消息。云端表结构及小程序视觉效果仍需部署和真机验证。
